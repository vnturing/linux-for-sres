Memory: free is the wrong number

By the end you can: tell healthy cache use from real memory pressure, and find an OOM kill after the fact.

U is utilization, S is saturation, E is errors. Lit lamps mark what this lesson examines.

Recall first

Before new material, pull these from memory. Struggling here is useful: it is what makes the earlier lesson stick.

High load with r=2 and b=14 mostly points toward…

  • Disk or network filesystems
  • A hot CPU thread
  • A busy hypervisor host
  • Severe kernel memory fragmentation

Blocked tasks in uninterruptible sleep, not runnable tasks, are the signature of I/O waits.

So far, CPU. The next resource is memory, where the most common mistake is reading the wrong column of free and panicking.

Free is not the number you want

Linux uses spare RAM as a file cache. That cache is “borrowed”: the kernel hands it back when programs need memory. So a healthy, busy server shows almost no free memory, by design. The kernel exposes a better figure. MemAvailable in /proc/meminfo, shown as the available column of free, is an estimate of how much memory is available for starting new applications without swapping.

Source: proc_meminfo(5), Linux man-pages. The field exists since Linux 3.14.
$ free -m
               total   used   free  shared  buff/cache  available
Mem:           15990   4210    180     120       11600      11300
flowchart LR
  RAM["Total RAM"] --> A["Anonymous memory: heaps and stacks, freed only by swapping or killing"]
  RAM --> PC["Page cache: file data, reclaimable"]
  RAM --> F["Free: unused"]
  PC --> AV["Available is roughly free plus reclaimable cache"]
  F --> AV

Here free is 180 MB, which looks alarming, but 11 GB is available. This host is fine.

The three questions for memory

  • Utilization: how much is genuinely in use? Look at available against total, not free.
  • Saturation: is the kernel struggling to find memory? Sustained nonzero si and so in vmstat 1 (swap in and out) is the classic sign. /proc/pressure/memory gives it directly: some and full lines, where full means every non-idle task was stalled.
  • Errors: did the kernel give up and kill something? The OOM killer logs to the kernel log.
$ dmesg -T | grep -i -E 'out of memory|oom|killed process'
$ journalctl -k --since "1 hour ago" | grep -i oom
$ ps aux --sort=-rss | head -5

Wording of OOM messages varies across kernel versions, so search loosely. In containers and systemd services, a memory limit can kill a process inside its cgroup while the host has plenty of memory. The log line names a memory cgroup, and the service shows exit status 137 (128 plus signal 9). We return to that in lesson 8.

Predict first. free -m shows 120 MB free and 9 GB available on a 16 GB host, and swap activity is zero. Is memory the problem?

Check your prediction
No. Available memory is large and nothing is swapping. The cache is simply doing its job. Exonerate memory and move to the next resource.

Drill on a throwaway box

Watch the cache give way

  1. Run free -m and grep -E 'MemAvailable|Cached|SwapTotal|SwapFree' /proc/meminfo. Write down available.
  2. Read a big file: cat /var/log/*.log > /dev/null or any large file. Run free -m again. Did buff/cache grow and free shrink while available barely moved?
  3. Only on a disposable VM, install stress-ng and run stress-ng --vm 1 --vm-bytes 80% -t 30s while watching vmstat 1 and cat /proc/pressure/memory. Then dmesg -T | tail.

Check yourself

Which free column best estimates memory for new applications?

  • free
  • buff/cache
  • available
  • shared

available accounts for reclaimable cache. free ignores it and so understates what is usable.

Sustained nonzero swap-in and swap-out in vmstat indicates what?

  • Healthy file cache warm-up
  • Memory saturation under pressure
  • A disk failing soon
  • Normal idle system behavior

Continuous swapping means the kernel cannot keep working memory in RAM. That is memory saturation.

Go to the source

If you read one thing on this topic, make it proc_meminfo(5), the Linux man page. It defines every field in /proc/meminfo, including MemAvailable, in the kernel developers’ own words.
