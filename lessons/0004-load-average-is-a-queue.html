Load average is a queue, not a percentage

By the end you can: read a load average, decide whether the CPU, the disk, or a hypervisor is behind it, and prove it with two commands.

U is utilization, S is saturation, E is errors. Lit lamps mark what this lesson examines.

Recall first

Before new material, pull these from memory. Struggling here is useful: it is what makes the earlier lesson stick.

Which of the ten commands prints per-CPU time breakdowns?

  • vmstat
  • iostat
  • pidstat
  • mpstat

mpstat -P ALL 1 shows each CPU separately, which exposes imbalance that averages hide.

In lesson 3, uptime gave you three numbers and we said “worth a quick look only”. Here is why, and what to run to turn those numbers into a diagnosis.

What the number counts

The load average is an exponentially damped moving average, over 1, 5, and 15 minutes, of the number of tasks that want to run. On Linux that includes tasks that are runnable on the CPU queue and tasks blocked in uninterruptible sleep, usually waiting on disk I/O. So a load of 30 can mean thirty things fighting for CPU, or thirty things stuck waiting on a slow disk. The number alone cannot tell you which.

Sources: the Netflix checklist from lesson 3, and Linux Load Averages: Solving the Mystery by Brendan Gregg, which traces why Linux includes uninterruptible tasks.

Compare the figure to the number of CPUs (nproc). Load 8 on an 8-CPU machine means roughly one task per CPU. Load 8 on 2 CPUs means a queue.

Splitting the ambiguity

Three commands you already know separate the causes:

  • vmstat 1: the r column is tasks waiting for or using CPU; compare it to the CPU count. The b column is tasks blocked in uninterruptible sleep. The wa and st columns are I/O wait and steal.
  • mpstat -P ALL 1: per-CPU view. One CPU at 100 percent and the rest idle is a single-threaded bottleneck that average utilization hides.
  • pidstat 1: which processes are consuming the CPU.

Steal matters on VMs and cloud instances: it is time the hypervisor gave your CPU to someone else. High steal means your VM is the problem, not your software.

Pressure Stall Information

Modern kernels expose a direct saturation signal. Read /proc/pressure/cpu:

$ cat /proc/pressure/cpu
some avg10=30.27 avg60=29.97 avg300=18.80 total=1620253162

The some line is the share of time in which at least one task was stalled waiting for CPU, averaged over the last 10, 60, and 300 seconds. That is saturation measured directly, with no guessing from load. The same interface exists for memory and I/O (/proc/pressure/memory, /proc/pressure/io), and per cgroup. If the files are missing, your kernel may not have PSI enabled.

Source: PSI: Pressure Stall Information, kernel documentation.

Predict first. vmstat shows r=2 and b=14 on a 4-CPU host with load 16. Is the CPU the problem?

Check your prediction
No. Only two tasks want CPU, but fourteen are blocked in uninterruptible sleep. The load is I/O wait. Look at iostat -xz 1, df -h, and whether a network filesystem is stuck. That is lesson 6.

Drill on a throwaway box

Make each cause on purpose

  1. Run nproc. In one terminal run vmstat 1; in another watch -n1 cat /proc/pressure/cpu.
  2. Start nproc * 2 copies of yes > /dev/null &. Watch r rise above the CPU count and the PSI some value climb. Kill them.
  3. Now create I/O wait: dd if=/dev/zero of=/var/tmp/f bs=1M count=4096 oflag=direct. Use /var/tmp, because /tmp is often memory-backed. Watch b and wa, and /proc/pressure/io. Then rm /var/tmp/f.
  4. Write down how r, b, and the two PSI files differed between the two experiments.

Check yourself

On Linux, load average counts tasks that are…

  • Only running on a CPU
  • Only waiting for network packets
  • Runnable or in uninterruptible sleep
  • Using over half a CPU

Linux counts runnable tasks and tasks in uninterruptible sleep, which is why disk waits raise load.

vmstat shows r=2 and b=14 on four CPUs. Where next?

  • Process CPU hogs
  • Disk and NFS
  • Network retransmits now
  • Kernel scheduler config

Few runnable tasks and many blocked ones point at I/O, so check disk and network filesystems.

PSI cpu shows some avg10=30.00. What does that mean?

  • Some task waited for CPU 30% of ten seconds
  • Thirty percent of all CPU cores were sitting idle
  • CPU usage averaged 30% over the last ten seconds
  • Load average equals 30 across every online core now

The some line is the percentage of time at least one task was stalled waiting for the CPU, averaged over the window.
