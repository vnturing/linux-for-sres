The first 60 seconds

By the end you can: run ten standard commands on a struggling server and place each result in the USE matrix.

U is utilization, S is saturation, E is errors. Lit lamps mark what this lesson examines.

Recall first

Before new material, pull these from memory. Struggling here is useful: it is what makes the earlier lesson stick.

Which signal counts discrete events such as dropped packets?

  • Utilization
  • Capacity
  • Errors
  • Saturation

Errors are counted events. Saturation is waiting work, and utilization is busy-ness.

Lesson 2 gave you four resources and three questions. Now you meet the ten commands that answer most of those questions in about a minute.

The checklist

The Netflix performance engineering team published the sequence they run when they log into a problem instance. It uses only standard tools. Here it is, with what each command answers.

Source: Linux Performance Analysis in 60,000 Milliseconds, Netflix TechBlog. Several commands need the sysstat package.
$ uptime
$ dmesg | tail
$ vmstat 1
$ mpstat -P ALL 1
$ pidstat 1
$ iostat -xz 1
$ free -m
$ sar -n DEV 1
$ sar -n TCP,ETCP 1
$ top

CommandAnswersLook for
uptimeIs demand rising or falling?1, 5, 15 minute load. A 1-minute figure far below the 15-minute one means you may have arrived after it passed.
dmesg | tailErrors, directlyOOM kills, TCP drops, disk errors. The Netflix team says not to skip it. Use dmesg -T for readable times; it may need sudo.
vmstat 1CPU, memory, swap, I/O at a glancer above CPU count; si/so nonzero; wa and st high.
mpstat -P ALL 1Per-CPU balanceOne CPU pegged while others idle: a single-threaded bottleneck.
pidstat 1Which processThe rolling per-process CPU view; it does not clear the screen like top.
iostat -xz 1Storage I/ORising await, deep queues, heavy throughput.
free -mMemoryThe available column, not free.
sar -n DEV 1Network throughputRx and Tx against the interface speed.
sar -n TCP,ETCP 1TCP healthRetransmits, new connections per second.
topSanity checkAnything the others missed.

Run each with a one-second interval and let it print a few lines before pressing Ctrl-C. The first line of vmstat, mpstat, and iostat shows averages since boot; read the lines after it.

Install the tools before the crisis

Gregg makes a pointed argument in his “Linux Crisis Tools” post: installing tools mid-outage fails in surprising ways. His made-up example has a package install that cannot even resolve repositories because of a broken apt configuration. Put the tools in your server images ahead of time. His list, with Ubuntu package names, is reproduced on the first-60-seconds reference.

Linux Crisis Tools, Brendan Gregg, March 2024.

Predict first. uptime shows load averages of 28, 24, and 3 on a 16-core host. What does that tell you, and what do you run next?

Check your prediction
Load is the 1-minute figure first: 28, well above 16 cores, and it has been climbing for over ten minutes since the 15-minute figure is only 3. The problem is recent and ongoing. Run dmesg | tail for errors, then vmstat 1 to see whether r exceeds 16 (CPU) or b is high (blocked on I/O).

Drill on a throwaway box

Idle versus loaded

  1. Use a disposable Linux VM, not a shared or production machine. Install the tools: sudo apt install sysstat procps on Debian or Ubuntu.
  2. Run all ten commands while the machine is idle. Note a baseline value from each.
  3. In another terminal start load, for example yes > /dev/null & once per core. Run the ten again.
  4. Stop the load with kill %1 (and the others). For each command write one line: did it change, and which USE cell does that fill?

Check yourself

uptime shows load 2.1 over one minute versus 20.4 over fifteen. What is likely?

  • The load is climbing right now.
  • The CPU hardware is failing soon.
  • Nothing can be concluded from load.
  • The problem has probably already passed.

The 1-minute figure is far below the 15-minute one, so load has fallen. You may have logged in after the event.

Why look at dmesg early in the sequence?

  • It lists every running process by CPU.
  • It measures per-device disk latency over time.
  • It can reveal OOM kills and drops.
  • It resets all counters for later comparisons.

Kernel messages carry direct evidence such as OOM kills and dropped connections, which are errors in USE terms.
