Network: refused, timed out, or slow?

By the end you can: classify a connectivity failure from one command’s behavior and pick the next check.

U is utilization, S is saturation, E is errors. Lit lamps mark what this lesson examines.

Recall first

Before new material, pull these from memory. Struggling here is useful: it is what makes the earlier lesson stick.

In iostat, which figure includes request queueing time?

  • await
  • rkB/s
  • tps
  • wkB/s

await is the average time a request takes including time spent queued, so rising await signals saturation.

Three resources done; the fourth is the network. Network debugging is a tangle unless you sort the symptom first, and one word does most of the sorting.

Sort the symptom

When a client cannot reach a service, ask what the connection attempt did:

  • Refused, instantly. The host is reachable and replied that nothing accepts connections there. Either no process is listening on that address and port, or a firewall rule actively rejects it.
  • Hangs, then times out. Packets are going into a void: a firewall silently dropping them, a missing route, a cloud security group, or the host being down.
  • Connects, but slow. Loss and retransmissions, slow DNS, or an overloaded application.
flowchart TD
  C["Client cannot reach service"] --> N{"Does the name resolve?"}
  N -->|no| DNS["DNS or resolver: getent hosts, dig, resolv.conf"]
  N -->|yes| K{"What does connect do?"}
  K -->|"refused, instantly"| R["Host answered, nothing accepted: ss -tlnp, bind address, REJECT rule"]
  K -->|"hangs, then times out"| TO["Packets vanish: firewall DROP, route, security group, host down"]
  K -->|"connects but slow"| SL["Loss, retransmits, DNS delays, busy app: nstat, sar -n TCP,ETCP, tcpdump"]

Server side: is anything listening?

$ ss -tlnp               # listening TCP sockets and their processes
$ ss -s                  # socket summary
$ ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c

The classic cause of “refused” is a service bound to 127.0.0.1 instead of 0.0.0.0: it works on the box and nowhere else. ss -tlnp shows the bind address; -p needs root to show other users’ processes. In the state counts, many SYN-SENT mean outbound connects are not being answered, and a pile of CLOSE-WAIT means the application is not closing sockets. A large TIME-WAIT count alone is usually normal. For a listening socket, Recv-Q is the current accept queue; if it sits at the limit, the application is not accepting fast enough.

ss and nstat come from the iproute2 package, which is on Gregg’s crisis tools list.

Client side: test the path

$ getent hosts api.internal           # resolves the way applications do
$ dig +short api.internal             # asks DNS directly
$ curl -sv --connect-timeout 3 -o /dev/null http://api.internal:8080/
$ ip -s link show eth0                # errors and drops per interface
$ nstat -az | grep -i retrans         # kernel TCP retransmit counters
$ sudo tcpdump -ni any port 8080 -c 20

getent and dig can disagree, and the disagreement is a finding: getent follows the system’s name-service configuration (including /etc/hosts), while dig queries DNS only. When all else fails, tcpdump shows what is actually on the wire. Julia Evans’s zines on tcpdump and networking are the friendliest introduction.

Further reading: Linux debugging tools you’ll love (Julia Evans) covers netstat, tcpdump, and wireshark.

Predict first. curl fails immediately with “Connection refused”, and ss -tlnp shows the service on 127.0.0.1:8080. What is wrong?

Check your prediction
The service listens only on the loopback interface, so remote clients get refused. Change its bind address to 0.0.0.0 or the correct interface, and confirm with ss -tlnp again.

Drill on a throwaway box

Cause each symptom

  1. Refused: curl -sv localhost:9. Nothing listens on port 9, so it fails at once. Note the message.
  2. Timeout: curl -sv --connect-timeout 3 10.255.255.1. Depending on your network this times out or reports the network unreachable; note which, and how long it took.
  3. Bind address: python3 -m http.server 8080 --bind 127.0.0.1 &. Run ss -tlnp, then curl using the machine’s LAN address. Restart it without --bind and repeat.

Check yourself

An instant “connection refused” most likely means what?

  • Packets are silently dropped en route
  • The DNS name failed to resolve
  • Host replied; nothing accepted the connection
  • Retransmissions are overwhelming the whole link

A refusal is an answer: the host is up and reachable, but no listener accepted, or a rule rejected it.

A service listening only on 127.0.0.1 is reachable from…

  • Only that same machine
  • Every host on LAN
  • Any host on internet
  • Only hosts in VPC

Loopback addresses never leave the machine, so remote clients cannot connect.
