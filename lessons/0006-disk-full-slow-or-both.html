Lesson 4 left a trail: blocked tasks usually mean slow storage. Storage is actually two resources, and mixing them up wastes the most time.

Capacity and speed are different resources

Capacity is how much room is left. Its failure is loud: writes fail with ENOSPC, and databases and loggers fall over. I/O speed is how quickly the device serves requests. Its failure is quiet: everything just gets slow. Treat them as two rows in your USE matrix.

Capacity: three checks, in order

flowchart TD
  W["No space left on device"] --> Dq{"df -h shows 100 percent?"}
  Dq -->|no| I{"df -i shows 100 percent inodes?"}
  I -->|yes| I2["Too many small files: find the directory"]
  I -->|no| Q["Check quotas, a read-only remount, or a different mount"]
  Dq -->|yes| U{"Does du -xh find the space?"}
  U -->|yes| T["Rotate or trim the big files"]
  U -->|no| O["lsof +L1: deleted files still held open"]

$ df -h                      # blocks: which filesystem is full?
$ df -i                      # inodes: out of files, not bytes?
$ du -xh --max-depth=1 /var 2>/dev/null | sort -h | tail
$ lsof +L1                   # deleted files still held open
$ journalctl --disk-usage    # the journal itself can be the culprit

Two traps catch nearly everyone once. First, a filesystem can run out of inodes while df -h shows plenty of free bytes, usually from millions of tiny files, and the error message is the same. Second, a process can keep writing to a file that someone deleted. The name is gone, so du cannot see it, but the space stays allocated until the process closes it or exits. When df says full and du cannot account for it, run lsof +L1, which lists open files whose link count is below one. Restarting the holder, or truncating through its file descriptor under /proc, releases the space; know the consequences before choosing.

Speed: reading iostat

$ iostat -xz 1

Focus on three things per device: await (average time per request, including queueing; in newer sysstat this is split into r_await and w_await), the average queue size (aqu-sz, called avgqu-sz in older versions), and throughput. Compare latency against what the device should deliver. Be careful with %util: per the iostat man page, near 100 percent means saturation only for devices that serve requests one at a time; modern SSDs and RAID arrays serve requests in parallel, so a high figure there does not by itself mean a limit has been reached. For a direct signal, read /proc/pressure/io. Errors live in dmesg: I/O errors, and a filesystem remounted read-only.

To find who is doing the I/O, pidstat -d 1 shows per-process reads and writes.

Netflix’s post covers reading iostat output on a real production host: Linux Performance Analysis in 60,000 Milliseconds.

Predict first. df -h shows /var at 100 percent, but du -xh /var adds up to about 40 percent. What is happening and what finds it?

Check your prediction
A deleted file is still held open by a running process, so its space is allocated but invisible to du. lsof +L1 lists it along with the process. Often it is a log file removed without restarting the logger.

Drill on a throwaway box

Create the invisible file

  1. dd if=/dev/zero of=/var/tmp/big bs=1M count=500
  2. tail -f /var/tmp/big > /dev/null & then rm /var/tmp/big
  3. Compare df -h /var/tmp (space still used) with du -sh /var/tmp (not counted). Run lsof +L1 and find the tail process.
  4. kill %1 and run df -h /var/tmp again: the space returns.

Check yourself

df reports a full filesystem but du totals far lower. Likeliest cause?

  • Deleted files held open
  • A failing storage controller
  • Corrupted inode tables everywhere
  • Misreported kernel block sizes

Space from deleted files is not freed until the last open handle closes, and du cannot see unlinked files.

Writes fail with ENOSPC but df -h shows free space. What next?

  • Reboot the host
  • Run df -i
  • Drop all caches
  • Resize the swap

Inode exhaustion gives the same error with free bytes. df -i shows inode usage.
