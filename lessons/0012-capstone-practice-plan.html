Capstone: practice under the clock

By the end you can: run timed troubleshooting scenarios, log them in a reusable format, and schedule the review that makes the skills stick.

U is utilization, S is saturation, E is errors. Lit lamps mark what this lesson examines.

Recall first

Before new material, pull these from memory. Struggling here is useful: it is what makes the earlier lesson stick.

What should come before the first diagnostic command?

  • A short problem statement
  • A full system reboot
  • A kernel parameter change
  • A package upgrade run

A problem statement gives the investigation direction and keeps you from thrashing.

You have a method, four resources, ten first-minute commands, service and process tools, shell speed, and an incident order of operations. Reading does not make these automatic. Practice on a clock does.

Practice on real broken servers

SadServers gives you a real Linux server with a problem and a check that confirms when you have fixed it, much like coding-interview practice but for operations. Its scenarios range across Linux administration, web servers, databases, and containers, and many people use it to prepare for SRE interviews. Start with the easier Linux and Bash scenarios, and give yourself a time limit.

The log you keep for every scenario

Write a short entry each time. This is lesson 1’s problem statement, extended.

Scenario / date / time taken:
Problem statement (symptom, baseline, change, scope):
Hypotheses, in order:
Resources checked and exonerated (U / S / E):
Commands that mattered:
Root cause:
What I did not know and had to look up:
What I would automate or pre-install:

Spacing is the feature

Rereading feels productive but fades fast. Retrieval on a schedule is what builds durable skill. After each scenario, redo it from scratch after 3 days, then 7, then 21, without notes. Mix scenario types, so you practice choosing the right tool and not only using the last one you learned.

  Dq --> A

Where to learn from other people

Wisdom comes from outside your own practice. SREcon, run by USENIX, is the field’s main conference series, and its talks are a window into how experienced teams think. SRE Weekly is a newsletter about keeping services available. Reading incident write-ups regularly builds the pattern library that makes the first minute faster.

A mixed check across the course

Which command’s output best reveals a deleted-but-open file?

  • lsof +L1
  • df -i
  • free -m
  • mpstat -A

lsof +L1 lists open files whose link count is below one, which are files deleted but still held open.

Load is high, r is low, and b is high. Which resource?

  • CPU run queue
  • Storage or I/O
  • Memory page cache
  • Network packet retransmits

Few runnable and many blocked tasks mean waiting on I/O rather than on the CPU.

A client gets an instant refusal. What does that imply?

  • Packets silently vanish en route
  • The host sent a reply
  • DNS returned an empty answer
  • TCP retransmits are rapidly climbing

Refusal is a reply: the host was reached, and no listener or a reject rule answered.

What belongs in the first four lines of an incident note?

  • Symptom, baseline, change, scope
  • Hostnames, versions, owners, budgets
  • Suspects, culprits, apologies, forecasts
  • Tools, flags, aliases, shortcuts

These four lines point you toward a resource and a hypothesis before the first command runs.
