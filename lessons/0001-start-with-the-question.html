Module 1: Think before you type. Lesson 1 of 12. About 8 minutes.

Start with the question, not the tool

By the end you can: write a four-line problem statement and a ranked hypothesis list before you touch the keyboard.

U is utilization, S is saturation, E is errors. Lit lamps mark what this lesson examines.

This is the first lesson, so there is nothing to recall yet. Everything later hangs off the habit built here.

The 3 a.m. page

A page fires: checkout API p99 latency is 4 seconds on api-7. You have a shell on the box. Most engineers type top. That is not wrong, only early. A command is an answer, and you have not yet decided which question you are asking.

Under pressure, the failure is rarely ignorance of a tool. It is thrashing: running commands because they exist, collecting numbers nobody asked for, and losing the thread. The fix is to put a short, boring ritual in front of the first command.

Four lines before the first command

Write these down in a scratch file or the incident channel. It takes about a minute and it pays for itself.

LineQuestion it forcesExample
SymptomWhat exactly is wrong, measured how?p99 latency 4 s, up from 300 ms
BaselineHas this ever been fine?Fine until about 14:05 today
ChangeWhat changed recently: code, config, load, hardware?Deploy at 14:03, traffic up 20 percent
ScopeOne host, one service, or everything?api-7 only; api-3 looks normal
The first three questions follow Brendan Gregg’s Problem Statement Method, listed in his Linux Performance Tools tutorial. Scope is our addition.

Notice what this already does. “Only api-7” suggests something local to the host. “After the deploy” suggests code or config. You have not run a command and you already have a direction.

A loop, not a list

Diagnosis is a loop. You hold a few ranked hypotheses, run the cheapest command that tells two of them apart, and let the result narrow the list. Google’s SRE book frames troubleshooting the same way: as a process you can learn and teach, not a gift.

flowchart LR
  S["Symptom: what, since when, who is affected"] --> H["Rank two or three hypotheses"]
  H --> C["Run the cheapest command that tells them apart"]
  C --> Dq{"Did it rule something in or out?"}
  Dq -->|yes| N["Narrow the list, or mitigate"]
  Dq -->|no| H
  N --> H

One more idea belongs in the loop from day one: exonerate. When you check a resource and find it healthy, say so out loud. Ruling something out is progress, because it shrinks the search. Netflix’s performance team makes the same point in their first-minute checklist, which we meet in lesson 3.

Predict first. Latency rose right after a 14:03 deploy. Name two cheap observations that would separate “the new code is slow” from “this host is overloaded”.

Check your prediction
Compare with a host that has the old code and similar traffic (scope), and check whether the host’s CPU, memory, disk, or network show strain at all (resources). If other hosts on the new code are slow too, suspect the code. If only this host is strained, suspect the host or its traffic share.

Drill on paper

Write it before you run it

  1. Take the 3 a.m. page above, or a real incident you remember.
  2. Fill in Symptom, Baseline, Change, Scope in four short lines.
  3. Write two or three hypotheses, most likely first.
  4. For the top one, write the single cheapest check that would confirm or kill it. Do not run anything yet.

Keep this note. In lesson 12 you will turn it into a template.

Check yourself

You’re paged for slow responses on api-7. What comes before the first command?

  • Open top and carefully scan every process.
  • State symptom, baseline, recent changes, and scope.
  • Restart the service, then investigate the cause.
  • Install every available profiling tool before proceeding.

A short problem statement points you toward a resource and a hypothesis. Opening top first is not wrong, just unguided, and restarting first can destroy the evidence.

What does exonerating a resource buy you?

  • Proof the application code is faulty.
  • Permission to skip all remaining checks.
  • A shorter list of remaining suspects.
  • A faster kernel under heavier load.

Each resource you rule out shrinks the search space and tells you where the next command should point.
