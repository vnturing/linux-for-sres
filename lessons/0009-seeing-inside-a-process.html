What does a restart loop eventually trip in systemd?

  • The start rate limit
  • The kernel panic timer
  • The journal size cap
  • The cron scheduler daemon

Repeated fast restarts hit the start limit, after which the unit stays failed until reset-failed.

Lesson 8 told you whether a service is running and how it last ended. When it is running but stuck or wrong, you need to look inside the process. Linux makes that unusually easy, because the kernel exposes processes as files.

The process as a directory

Every process has a directory /proc/PID. A few entries earn their keep in a crisis:

  • /proc/PID/status: state, memory, threads.
  • /proc/PID/fd/: one entry per open file or socket.
  • /proc/PID/limits: resource limits, including Max open files.
  • /proc/PID/cmdline, cwd, exe: what it is and where it runs.
$ ps -o pid,stat,wchan:24,rss,cmd -p 4242
$ ls /proc/4242/fd | wc -l
$ grep 'open files' /proc/4242/limits
$ lsof -p 4242 | head
$ lsof -i :8080

The STAT letter matters. R is running or runnable, S is sleeping and can be interrupted, and D is uninterruptible sleep, usually waiting on I/O inside the kernel, which you cannot kill. A process stuck in D sends you back to lesson 6: check storage and network filesystems. wchan names the kernel function it is waiting in. A Z is a zombie, already dead, waiting for its parent to collect it.

A classic production outage: a service slowly leaks file descriptors until it hits its limit, then fails with “too many open files”. Compare the count in /proc/PID/fd to the limit in /proc/PID/limits. For a systemd service the limit is set by LimitNOFILE=, not by your shell’s ulimit.

strace: ask the process what it is doing

flowchart TD
  H["Service is up but stuck or wrong"] --> S["ps -o stat,wchan -p PID"]
  S --> Dq{"State D?"}
  Dq -->|yes| K["Waiting in the kernel on I/O: iostat, dmesg, NFS"]
  Dq -->|no| C{"Using CPU?"}
  C -->|yes| P["Hot loop: perf top or strace -c"]
  C -->|no| W["Blocked in a syscall: strace -f -p PID shows which"]

$ sudo strace -f -tt -T -p 4242 -e trace=network,file -o /tmp/s.txt   # Ctrl-C after ten seconds
$ sudo strace -c -p 4242                                              # summary table of syscalls

Every interaction between a process and the outside world is a system call, and strace prints them with their return values. Read the failures. A line like openat(..., "/etc/app/x.yaml") = -1 ENOENT says a file is missing. connect(...) = -1 ETIMEDOUT says a dependency is unreachable. A process that is parked in futex or poll is waiting for something else to happen.

strace works by stopping the process at every syscall, so it can slow a busy process noticeably. Attach briefly, filter with -e trace=, and detach. Where installed, perf and bpftrace from the crisis-tools list trace with much less overhead.

Julia Evans’s zine Linux debugging tools you’ll love is the gentlest introduction to strace and perf, written for people who have never used them.

Drill on a throwaway box

Inspect your own shell

  1. ls -l /proc/$$/fd shows your shell’s open files; grep 'open files' /proc/$$/limits shows its limit.
  2. sleep 300 & then ps -o pid,stat,wchan:24,cmd -p $!. What is it waiting in?
  3. strace -f -e trace=openat cat /etc/hostname. List every file it opened, including the libraries.
  4. strace -c ls /usr/bin > /dev/null and find the most frequent syscall. Then kill %1.

Check yourself

A process stays in state D. What is it waiting for?

  • Kernel-level disk or network I/O
  • A user keypress at terminal
  • Its parent process to exit
  • A scheduled timer to fire

D is uninterruptible sleep, typically blocked on I/O inside the kernel, such as a stuck disk or network filesystem.

Which file shows a running process’s open-files limit?

  • /proc/PID/status
  • /proc/PID/cmdline
  • /proc/PID/limits
  • /proc/PID/environ

/proc/PID/limits lists every resource limit for that process, including Max open files.
