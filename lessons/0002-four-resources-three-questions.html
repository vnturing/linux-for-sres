Resources

A server does its work with a small set of physical resources: CPU, memory, storage (both its speed and its capacity), and network interfaces. Nearly every “the server is slow” incident is one of these running out, or something misbehaving because one did.

Three questions per resource

Brendan Gregg’s USE method fits in one sentence: for every resource, check utilization, saturation, and errors.

  • Utilization: how busy is the resource, as a fraction of its capacity, over an interval?
  • Saturation: is there more work waiting than the resource can serve? Usually a queue length or time spent waiting.
  • Errors: are discrete failure events being counted: dropped packets, I/O failures, killed processes?
Source for the one-sentence form: The USE Method, FreeBSD Journal (Gregg). A full Linux checklist is at brendangregg.com/USEmethod/use-linux.html.

The method works because it starts from questions, not tools. You will not overlook disk errors just because you happen to be fluent in a CPU tool.

Why errors and saturation come first

Netflix’s first-minute guidance is to look for errors and saturation first, because both are easy to interpret, and then at utilization. A nonzero error count is a finding. A growing queue is a finding. A utilization figure of 60 percent, by contrast, means very little until you know what the resource was asked to do.

Utilization is also easy to misread, because it is an average over an interval. A resource can average 45 percent over a minute and still sit at 100 percent in short bursts that make requests queue. Saturation is what exposes that.

flowchart TD
  P["Symptom"] --> R["Pick a resource: CPU, memory, disk, network"]
  R --> E{"Errors?"}
  E -->|yes| X["Fault found: chase the error source"]
  E -->|no| S{"Saturated?"}
  S -->|yes| Y["Bottleneck suspect: find who is queued"]
  S -->|no| U{"Utilization high?"}
  U -->|yes| Z["Near the limit: watch for saturation"]
  U -->|no| O["Resource exonerated: next resource"]
  O --> R

Predict first. A CPU averages 45 percent utilization over a minute, but users report stalls. Which signals could still show trouble?

Check your prediction
Saturation: a run queue that spikes above the CPU count, or PSI cpu pressure. Also look per CPU, since one core pinned at 100 percent (a single-threaded bottleneck) hides inside a low average, and steal time if this is a VM.

Check yourself

A run queue longer than the CPU count is which USE signal?

  • Utilization
  • Saturation
  • Errors
  • Throughput

Work is waiting for a resource that cannot serve it yet. That is saturation, shown as a queue.

Writes fail with ENOSPC while the disk is only 40 percent busy. Which resource is exhausted?

  • Network packet loss
  • CPU scheduler delay
  • Memory page reclaim
  • Storage capacity exhausted

Busy-ness of the device and free capacity are separate resources. Capacity ran out even though the device had spare time.

Why read errors and saturation before utilization?

  • Utilization numbers are unreliable on every kernel.
  • Errors and saturation never need any tooling.
  • They are easy to interpret and decisive.
  • Utilization can only be measured after reboots.

Errors and saturation are usually direct evidence. Utilization needs context before it means anything.
