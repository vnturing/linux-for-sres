Which first-minute command reveals OOM kills?

  • dmesg
  • uptime
  • free
  • top

Kernel messages record OOM-killer events, so dmesg is the quickest place to confirm one.

You can now read a machine and slice its logs. The last skill is deciding what to do while someone is waiting. The order of operations matters more than any single command.

Two goals that compete

An incident has two jobs: restore service and learn the cause. They compete. A restart often restores service and erases the evidence at the same moment. The discipline is to separate them: capture a small, fast snapshot first, then mitigate, then investigate from what you saved.

flowchart TD
  A["Alert or report"] --> B["Capture about 60 seconds of evidence"]
  B --> C{"Is there a recent change to undo?"}
  C -->|yes| Dq["Roll back"]
  C -->|no| E["Shed load, drain, or scale"]
  Dq --> F{"Recovered?"}
  E --> F
  F -->|no| G["Restart only after evidence is saved"]
  F -->|yes| H["Diagnose from the evidence, fix, write it down"]
  G --> F

The evidence snapshot

This runs in well under a minute and writes to one directory. If the disk is the problem, point it at /dev/shm or stream it off the host instead.

$ d=/var/tmp/ev-$(hostname)-$(date +%Y%m%dT%H%M%S); mkdir -p "$d"
$ { date; uptime; free -m; vmstat 1 5; mpstat -P ALL 1 3; iostat -xz 1 3
$   df -h; df -i; ss -s; ps auxwwf; } > "$d/snapshot.txt" 2>&1
$ dmesg -T > "$d/dmesg.txt"
$ journalctl --since "1 hour ago" --no-pager > "$d/journal.txt"

Gregg’s “Linux Crisis Tools” post includes a made-up outage in which the team reverts a VM snapshot to restore the site. It works, but all the logs and command output from the broken state vanish with it, and the problem returns hours later because the cause was never found. The lesson is general: whatever you do to mitigate, ask first what it destroys.

Source: Linux Crisis Tools by Brendan Gregg. The same post argues for pre-installing diagnostic tools on every server.

Choosing a mitigation

Prefer actions that are fast and reversible, in roughly this order:

  1. Undo the last change. Lesson 1 asked what changed recently for exactly this reason. Roll back the deploy or flag.
  2. Shed or redirect load. Drain the host from the load balancer, rate limit a noisy client, scale out.
  3. Restart, after the snapshot, and note the time.
  4. Change a limit or setting only when you understand what it does. Write down the old value first.

Keep a running timeline in the incident channel: what you saw, what you changed, when. It is the raw material for the postmortem, and it keeps a handoff from becoming guesswork. Google’s SRE book devotes whole chapters to emergency response, incident management, and blameless postmortems; they are listed in its table of contents.

Check your prediction
Run the 60-second evidence snapshot so the bad state is saved, roll back, and confirm that latency recovers. Post the timeline. Then diagnose from the saved evidence and the diff of the deploy, with the pressure off.

Drill on a throwaway box

Time your snapshot

  1. Paste the snapshot commands into a script, snap.sh, and run it with time. Aim for under a minute.
  2. Open the resulting files. Is anything missing that you would have wanted during lesson 4 to 7 problems? Add it.
  3. Keep the script with your dotfiles, ready to copy onto a server.

Check yourself

What do you capture before restarting a misbehaving service?

  • A snapshot of state and logs
  • Nothing, since restarts always fix everything
  • Only the version of the service
  • A screenshot of the whole dashboard

A restart can erase the evidence. A quick snapshot of state, kernel messages, and logs preserves it for diagnosis.

Which mitigation is usually fastest and most reversible?

  • Rewriting the whole application
  • Tuning kernel parameters live
  • Rolling back the change
  • Reinstalling the operating system

If a recent change likely caused it, rolling back restores a known state and can itself be undone.
