Services: systemd is your first responder

By the end you can: take a failing or flapping service from “it’s down” to an exit status and a log line in under two minutes.

U is utilization, S is saturation, E is errors. Lit lamps mark what this lesson examines.

Recall first

Before new material, pull these from memory. Struggling here is useful: it is what makes the earlier lesson stick.

Which tool shows who is listening on a TCP port?

  • ss -tlnp
  • df -i
  • iostat -x
  • dmesg -T

ss -tlnp lists listening TCP sockets with their processes, which answers “who owns this port”.

Lessons 4 to 7 read the machine. But the page is often phrased as “the service is down”. On almost every modern server, systemd is the thing that knows why.

A unit has a life cycle

systemd supervises each service as a unit. If you know its states, a status line stops being noise.

stateDiagram-v2
  [*] --> inactive
  inactive --> activating: start
  activating --> active: ExecStart running
  activating --> failed: exits or times out
  active --> failed: crash or killed
  failed --> activating: auto-restart
  failed --> inactive: stop or reset-failed

Two minutes of commands

$ systemctl status nginx                    # state, main PID, exit status, last log lines, cgroup
$ systemctl --failed                        # what else is broken?
$ journalctl -u nginx -e                    # jump to the end of this unit's log
$ journalctl -u nginx --since "15 min ago" -p warning
$ systemctl cat nginx                       # unit file plus any drop-ins, as systemd sees it
$ systemctl show -p NRestarts,ExecMainStatus nginx
$ journalctl -k --since "15 min ago"        # kernel log, for OOM kills

Read the status block top to bottom. Active: says whether it is failed, activating (auto-restart), or running. Main PID and the exit line say how it last ended. The final lines are the most recent journal entries. In a flapping service, those exit lines repeat.

Reading how it died

  • status=137 or “killed, status=9/KILL”: something sent SIGKILL. Check journalctl -k for the OOM killer or a cgroup memory limit (MemoryMax=), then look for a human or a watchdog.
  • status=143: SIGTERM, so a normal stop request.
  • status=1 or another small number: the application exited with its own error. Its own log is next.
  • 203/EXEC: systemd could not execute the binary. Wrong path, not executable, or a missing interpreter. The unit never started the program at all.

A service that dies and restarts repeatedly will eventually trip systemd’s start rate limit and stay failed, with a message about restarting too quickly. After fixing the cause, clear it with systemctl reset-failed and start again. After editing a unit file, run systemctl daemon-reload. Prefer systemctl edit to change a unit through a drop-in, so package upgrades do not overwrite your change.

The reference for every directive, including Restart= and the exit-status handling, is systemd.service(5).

Predict first. A service’s status repeats “Main process exited, code=killed, status=9/KILL” every two minutes. What do you check first?

Check your prediction
Something sends SIGKILL on a cycle. Check journalctl -k for OOM-killer lines and whether the unit has a MemoryMax=. If memory is not it, look for a watchdog, a timeout (TimeoutStopSec), or a deploy script that kills it.

Drill on a throwaway box

Make a flapping service

  1. sudo systemd-run --unit=flaky -p Restart=on-failure -p RestartSec=2 sh -c 'echo starting; sleep 3; exit 1'
  2. Run systemctl status flaky several times. Watch activating (auto-restart) alternate with activating and the restart count rise. In another terminal run journalctl -u flaky -f.
  3. Run systemctl show -p NRestarts flaky. Then sudo systemctl stop flaky.

Check yourself

Which command shows a unit file together with its drop-ins?

  • journalctl -u nginx
  • systemctl is-active nginx
  • systemctl status nginx
  • systemctl cat nginx

systemctl cat prints the unit file and every drop-in as systemd sees them. status shows the path but not the contents.

A service exits with status 137. What is most likely?

  • SIGKILL, often the OOM killer
  • A clean requested stop signal
  • A missing executable file path
  • An ordinary application error code

137 is 128 plus signal 9, so the process was force-killed, most often by the OOM killer or a memory limit.

Go to the source

If you read one thing on this topic, make it systemd.service(5). It defines how service units start, stop, restart, and report exit status. Search it for Restart= and exit status when something flaps.
